# CONN-CAMUNDA-MCP — Requirements

Every requirement this specification owns, with the proof that closes it. Delivery state and
public evidence for each ID are recorded in [`status.json`](status.json); this file defines what
each ID means. The design is in [`spec.md`](spec.md) and [`plan.md`](plan.md), the test contract
in [`test-spec.md`](test-spec.md), and the work order in [`tasks.md`](tasks.md).

| ID | Requirement | Verification |
|---|---|---|
| `CONN-CAMUNDA-MCP-R001` | **Connector reports its released version.** `camunda_mcp.__version__` equals the released `pyproject.toml` version and the bump configuration updates both. Caller chain: the installed `camunda-mcp` distribution metadata (`pyproject.toml` line 7) -> `__version__ = _v("camunda-mcp")` in `camunda_mcp/api_client.py:18`, imported by the code that builds `Api`; `camunda_mcp/__init__.py` defines no `__version__`. Shape: `camunda_mcp/api_client.py:18` takes `__version__` from `importlib.metadata.version`; the new test compares it with the `project.version` read from `pyproject.toml` and the bump configuration entry. | `tests/test_version.py::test_reported_version_matches_the_released_package` |
| `CONN-CAMUNDA-MCP-R002` | **One tool per engine REST operation.** The server lists 411 tools: one `camunda7_<operation>` per Operaton / Camunda 7 engine REST operation (386, the whole engine REST API of the deployed Operaton 1.0.3 engine, named from the upstream operation id), one `camunda8_<operation>` per Camunda 8 client method (24), plus `camunda_ingest_processes`. Every tool is typed (no `params_json` fallback). Caller chain: the `camunda-mcp` console script (`scion_sdk.cli:serve`) loads `camunda_mcp:connector` (`camunda_mcp/__init__.py`); its `verbose_targets` prefixes `camunda7` and `camunda8` yield one tool per public client method. Shape: `Camunda7Api` (`camunda_mcp/api/api_client_camunda7.py`) composes one class per REST area from `camunda_mcp/api/camunda7/`, each method one operation with path parameters, typed query filters and a `body` or multipart fields. | `tests/test_tool_surface.py::test_surface_is_one_tool_per_engine_operation` |
| `CONN-CAMUNDA-MCP-R003` | **No condensed or routed tools.** No tool is tagged `split-action`, takes an `action` argument or is untyped, and the retired `camunda_process`, `camunda_instance`, `camunda_task` and `camunda_deploy` tools are gone. Caller chain: `build_server("camunda_mcp")` -> the tools of `camunda_mcp/mcp/mcp_camunda.py` and the generated `camunda7_*` and `camunda8_*` tools. Shape: the only hand-written tool is `camunda_ingest_processes`; deploying is `camunda7_create_deployment` / `camunda8_deploy_resources`. | `tests/test_tool_surface.py::test_no_action_routed_or_untyped_tools` |
| `CONN-CAMUNDA-MCP-R004` | **Query and form values reach the engine in the form it parses.** Booleans are sent as lowercase `true`/`false` (Python's `True` made `latestVersion` return HTTP 400), list values as comma-separated strings, unset values are dropped, path parameters are escaped, a deployment's `resources` are multipart parts, and a failed call carries the engine's own error type and message. Caller chain: every `camunda7_*` tool -> `Camunda7Api.<operation>` -> `ApiClientBase._call` -> `ApiClientBase.request` (`camunda_mcp/api/api_client_base.py`). Shape: `_wire_params` converts the values; `_engine_error` adds the bounded engine message to the raised error. | `tests/test_wire_values.py::test_booleans_are_lowercase_and_unset_filters_dropped` |
| `CONN-CAMUNDA-MCP-R005` | **Tool-use contracts, links, data locations and business roles.** `camunda_mcp/connector_contracts.py` declares the business tasks (deploy a business process, retire a deployment, start, monitor, set variables, work the human task queue, hand over a task, work external tasks, correlate a message, broadcast a signal, evaluate a decision, recover an incident, ingest to the graph, verify the engine connection) as ordered tool steps with parameters, result fields and refusals, plus one single-step contract per operation, so every served tool is called by a contract step and named by a link; four data locations (process models, runtime, human task queue, history) name the engine, store, read tool, route parameter and federation key; two business roles (business process designer, human task worker). The declarations are served as `ontology://camunda-mcp/contracts.ttl`. Caller chain: `register_camunda_tools` (`camunda_mcp/mcp/mcp_camunda.py`) registers the resource -> `contracts_turtle()` -> `render_surface_turtle` (`camunda_mcp/_surface.py`). Shape: `camunda_mcp/connector_contracts.py` holds `CONTRACTS`, `LINKS`, `LOCATIONS` and `ROLES` built from the `ToolUseContract`, `ToolStep`, `Refusal`, `SurfaceLink`, `DataLocation` and `BusinessRole` types of `camunda_mcp/_surface.py`, which match the SDK surface-contract vocabulary; reuse `render_surface_turtle` for the Turtle. | `tests/test_surface_contracts.py::test_every_tool_is_called_by_a_contract_and_named_by_a_link` |
| `CONN-CAMUNDA-MCP-R006` | **Prompts are complete agent definitions and the business workflows are skills.** `camunda_mcp/prompts/` holds the operator agent `camunda-process-operator` and the business-role agents `camunda-business-process-designer` and `camunda-human-task-worker`; each states role, goal, tools and skills, data locations, guardrails (approval-required destructive tools, never-do rules) and outputs, and its `agent` object names only served tools, packaged skills and declared locations. Skills `camunda-deploy-business-process`, `camunda-run-and-monitor-instance`, `camunda-work-human-task-queue` and `camunda-incident-recovery` write up the proven workflows and name only served tools. Caller chain: the SDK content registrar serves `prompts/*.json` as MCP prompts and `skills/*/SKILL.md` as `skill://` resources. Shape: each `camunda_mcp/prompts/<name>.json` carries `identity`, `instructions.core_directive` (sections GOAL, TOOLS AND SKILLS, DATA, GUARDRAILS, OUTPUT) and an `agent` object (`kind`, `business_role`, `tools`, `skills`, `data.reads`/`data.writes`, `guardrails`, `outputs`); each skill is `camunda_mcp/skills/<name>/SKILL.md`; the SDK content registrar is reused, no serving code. | `tests/test_surface_contracts.py::test_prompts_are_complete_agent_definitions` |
| `CONN-CAMUNDA-MCP-R007` | **The BPMN, DMN and engine ontology rolls up to core by subclassing.** `camunda_mcp/ontology/camunda.ttl` models the BPMN 2.0 constructs (process, flow node, task kinds, gateways, events and event definitions, sequence and message flows, pools, lanes, data) and DMN decisions as the shape a workflow graph is generated from: each flow-node class carries `:dagNodeKind` and `:executedByTool`; the engine records (definitions, deployments, instances, user tasks, external tasks, jobs, incidents, variables, decision results) and their data location (`:heldByEngine`, `:deployedIn`, `:CamundaEngine`). Every class reaches a core class through `rdfs:subClassOf`; the file never imports the core ontology; every tool it names is served. Caller chain: the SDK serves the file as `ontology://camunda-mcp/camunda.ttl`. Shape: one Turtle file `camunda_mcp/ontology/camunda.ttl` in the core `http://knuckles.team/kg#` namespace with classes `:Bpmn*`, `:Dmn*` and `:Camunda*` subclassing core classes (`:ProcessModel`, `:TaskStep`, `:Concept`, `:Policy`, `:Document`, `:BusinessProcess`, `:Task`, `:Job`, `:Incident`, `:Application`), the annotation properties `:dagNodeKind`, `:executedByTool`, `:bpmnElement`, and the data-location properties `:heldByEngine`, `:deployedIn`; the SDK ontology serving is reused. | `tests/test_ontology.py::test_every_class_reaches_a_core_class` |
| `CONN-CAMUNDA-MCP-R008` | **Governed deploy sink for released process models (rollup).** Subsystem: connector `camunda-mcp`. The engine deploys graph-held process models to Camunda through governed write-back (`MEDULLA-CQ-ORCH-R703.3`). This connector executes released deploy change sets through the SDK governed write-back sink of `SCION-GOVERNED-WRITEBACK-R006`. It deploys only a change set that arbora approved and the engine released. The deploy business task of `CONN-CAMUNDA-MCP-R005` stays the interactive path; this sink is the governed path. Children `.1` to `.3`. Depends on: `SCION-GOVERNED-WRITEBACK-R006`, `CONN-CAMUNDA-MCP-R002`. | Rollup closes when `.1` to `.3` are verified. Root test: `tests/test_deploy_sink.py::test_released_change_set_deploys_once`. |
| `CONN-CAMUNDA-MCP-R008.1` | **Deploy sink executes a released change set.** Subsystem: connector write-back. Add `camunda_mcp/writeback_sink.py::CamundaDeploySink`, an implementation of the SDK governed write-back sink of `SCION-GOVERNED-WRITEBACK-R006`. Rule: each proposal of a released change set carries one BPMN 2.0 or DMN document, its SHA-256 digest and the model id. The sink calls `create_deployment` (`camunda_mcp/api/camunda7/deployment.py:11`) with the deployment name set to the model id. It sets `enable-duplicate-filtering` and `deploy-changed-only`, so a second release of the same documents creates no new definition version. A Camunda 8 target uses the deploy method of the `camunda8` client. Caller chain: arbora approval (`ARBORA-OPS-R865`) → engine release → the SDK sink runner → `CamundaDeploySink.execute`. Shape: one sink class. Depends on: none. | A released change set of two documents makes one deploy call. Test: `tests/test_deploy_sink.py::test_released_change_set_deploys_once`. |
| `CONN-CAMUNDA-MCP-R008.2` | **Deploy sink refusal and evidence.** Subsystem: connector write-back. Rule: a change set that is not released refuses `CHANGE_SET_NOT_RELEASED` before any API call. A payload whose SHA-256 differs from the proposal digest refuses `PAYLOAD_DIGEST_MISMATCH` before any API call. The result maps each proposal external id to the deployment id and the deployed definition ids and versions. Caller chain: `CamundaDeploySink.execute` → the SDK sink runner result. Shape: refusal codes and the result mapping in `writeback_sink.py`. Depends on: `CONN-CAMUNDA-MCP-R008.1`. | Both refusals make no API call. Test: `tests/test_deploy_sink.py::test_unreleased_or_mismatched_change_set_refuses_without_calls`. |
| `CONN-CAMUNDA-MCP-R008.3` | **Register the deploy sink and prove the path.** Subsystem: connector registration. Pass `CamundaDeploySink` to the `Connector(...)` call in `camunda_mcp/__init__.py` as the write-back sink. The test drives a released change set through the SDK sink runner against recorded API responses. It asserts one deployment and, on a second release, no new definition version. Caller chain: `camunda_mcp:connector` → SDK sink runner → `CamundaDeploySink.execute`. Shape: one registration argument and one test. Depends on: `CONN-CAMUNDA-MCP-R008.2`. | The registered connector exposes the sink and the second release is idempotent. Test: `tests/test_deploy_sink.py::test_registered_sink_is_idempotent_on_rerelease`. |
